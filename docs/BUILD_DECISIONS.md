## Phase 2 — E-commerce

19. **Higgsfield endpoint is unverified.** `worker/lib/visual.ts` posts to `HIGGSFIELD_API_URL` with `hf-api-key`; without a key every image is stored as `planned` with its prompt, so the cards still show what would be made. Verify the endpoint before the first paid run.

24. **The pitch selection rules live in code** (`PITCH_RULES` in `worker/lib/pitch.ts`) and in the pitch system prompt, not as an editable playbook yet, so a playbook edit can't silently loosen the $10 / 35% bar.

## Phase 3 — Content

27. **Ideas live in a new `social_ideas` table.** The older `content_ideas` (schema_082) is per CRM client and plan, so reusing it would have mixed two products. Ideas aren't an approval: "Add to plan" is Marq's tap.
28. **"No blank page"** works three ways: the Ideas tab runs Idea & Script itself the first time an account has none; the nightly `ideas` step tops up any account under 5 open ideas (2 accounts a night, so spend stays small); and **More ideas** runs it on demand.
29. **Breakouts are 3× the account average, flops are under ⅓**, the same thresholds Content Analytics already used. A breakout writes a `content_briefs` row; a 👍 on a post writes a `liked` brief. Both feed the next ideas run as positive examples.
30. **"Pull this post" doesn't fake an API.** The Instagram Graph API and TikTok Content Posting API publish but can't delete or archive. Pull opens the post with one line of instructions, and "I pulled it" sets `social_posts.pulled_at`.
31. **Clips render with our own ffmpeg service** (`render/`, sized for Cloudflare Containers). Higgsfield's API exposes reframe and upscale but no verified endpoint for cutting ranges and burning captions. The Worker builds the ffmpeg arguments (pure, tested) and sends signed download and upload URLs plus an HMAC-signed callback. It's behind `CLIP_RENDER=on` + `RENDER_URL`; with those off, the plan-only path is unchanged. **Left to do:** deploy the container and set `RENDER_URL`, `RENDER_SECRET` and `CLIP_RENDER`. The container wiring wasn't added to `wrangler.jsonc`, so the main deploy can't break.
32. **The Publisher prefers the rendered file** (`rendered_path`), then the old `edited_url`, then the raw upload.
33. **Variant rule enforced at scheduling:** after the Post Planner's slots are applied, the second of any identical caption + video pair going to two accounts on the same day is held (`publish_status = failed` with the reason), so Marq changes it instead of posting spam.
34. **Own accounts use the existing owner value `mastermind`** (the schema_100 check), not `masterminds`. "Add Masterminds, Made by Marq + personal accounts" seeds the six IG/TikTok rows with written voices, not connected.
35. **The content kit is an approval** (`content_kit`). Approving it puts the 9 posts on the Plan, labelled [A]/[B] for the two directions, timed from the 2-week plan. They're attached to the brand's accounts if those exist, otherwise left unassigned. Creating the accounts stays a manual checklist.

## E-commerce architecture addendum (LOCKED) — one Shopify store, one site per product

68. **E-commerce architecture: one Shopify backend per owner, one Cloudflare site per product, checkout via cart permalinks with `mm_site` attribution.** The Launcher already used one shop plus a Pages deploy per brand, so this change adds a `ecom_sites` row per launched page instead of rebuilding Phase 2. Client Stores (subscribers on the E-commerce tier) follow the same model: one Shopify connection each, many sites.
69. **The cart permalink format was checked against shopify.dev ("Create cart permalinks")**: `/cart/{variant}:{qty}`, `attributes[key]=value` (arrives as `note_attributes`), `discount=CODE` (a comma means several codes, so a code containing one is dropped), plus `ref` and `note`. UTM tags aren't a documented permalink parameter, so they travel as cart attributes (`attributes[utm_source]`…). Everything goes through `buildCheckoutUrl()` in `worker/lib/sites.ts`, which has tests.
70. **UTM tags come from the visitor's landing URL, so they're added in the browser.** A small inline script on every generated site copies `utm_*` and `discount` from the page URL into the Buy link, shows a variant picker when the product has more than one variant, and sends `view` / `buy_click` beacons. The quality gate's "no external scripts" rule still holds because the script is inline.
71. **The beacon is a new public endpoint, `POST /api/ecom/beacon`**, not the existing `/api/marketing/visits`, which reads Cloudflare Web Analytics and needs the owner's login. It uses `navigator.sendBeacon` (text/plain, so no CORS preflight) and calls the `ecom_site_hit()` RPC, which only counts for a slug whose site is live. The RPC is service-role only.
72. **The quality gate runs twice.** The draft gate still wants `href="#checkout"`, because a draft has no variant yet. After the Launcher points the buttons, `checkoutGate()` fails the launch unless every Buy button is a cart permalink to the shared store's domain with `mm_site` set.
73. **Attribution order: `mm_site` cart attribute → `attributes[mm_site]` in the landing URL → the referring site's host matched against the site's domain or pages.dev URL.** Anything else is "Unattributed". If more than 20% of the last 7 days' orders are unattributed (with at least 5 orders, so a single stray order doesn't flag), an amber `unattributed_orders` flag is raised (`DEFAULT_THRESHOLDS.unattributedPct`).
74. **`ecom_orders.brand_id` no longer has to be filled in (schema_127).** The old code tried to insert unmatched orders without a brand and silently lost them to the NOT NULL constraint. Relaxing it changes no data, and isn't a drop, rename or retype; it's what lets "Unattributed" orders be kept and counted.
75. **"Stores" → "Sites" in labels and data, but not in route keys or columns.** The nav and headings say Sites, and new data lives in `ecom_sites`. The screen key stays `ecom-stores` (links and flags point at it), and HQ's "Sites per product" is stored in the existing `system_controls.stores_per_product` column rather than a renamed one (rule: never rename a column).
76. **Shopify auth goes through one helper.** `getShopifyToken` / `withShopify` in `worker/lib/shopify.ts` handle both connection types: (a) a legacy `shpat_` token, or (b) a Dev Dashboard app's Client ID + Secret. For (b) it uses the client credentials grant (`POST /admin/oauth/access_token`, about 24 h tokens), caches the token in the same vault record, refreshes it 5 minutes before expiry, and forces a refresh and retries once on a 401. Webhook HMACs use the client secret for (b) and the API secret key for (a). Verified against shopify.dev's "Get API access tokens for Dev Dashboard apps". That grant only works when the app and the store are in the same organization, and the Setup error explains `shop_not_permitted`.
77. **Domains: there's no API purchase, so buying is a one-tap checklist step.** Cloudflare's API attaches domains that are already in the account to a Pages project (`POST …/pages/projects/{name}/domains`), but it has no public call to register a new one. So "Buy domain (~$10–15/yr)" → checkSpend → an Inbox approval → "Buy it at Cloudflare ↗" + "I bought it" (which records $12 in the Ledger) → "Connect" → "Check". Sites run on `*.pages.dev` until then. Connecting obeys DRY_RUN.
78. **The shared-store trade-offs are built in.**
    - Every site's footer reads "Checkout securely powered by {the Shopify store's name}" and links to the store's own `/policies/refund-policy`, `/shipping-policy`, `/privacy-policy` and `/terms-of-service`, plus its contact email. All of these are read from the shop at launch.
    - Store Builder is told never to state its own return, shipping or guarantee terms.
    - The Setup card's first step is to name the store as a neutral parent brand and set the checkout and email logo.
79. **Prohibited and trademark filter.** It's a keyword-level list drawn from Shopify's Acceptable Use Policy and the Shopify Payments prohibited list: weapons, drugs and supplements, tobacco and vape, adult, health claims, gambling, counterfeits and dupes, and well-known brand names. It runs in Scout's parser (the row is dropped with the reason), in the Pitch hard filter, and in Scout's prompt. A false alarm just means the product isn't pitched; a human can still add it by hand.
80. **Site slugs are globally unique**, because the public beacon finds a site by slug. A build launched before this addendum keeps its Pages project name as its slug, so its live URL doesn't change.

81. **Texting replies have a free default.** With no `XAI_API_KEY`, the two-way texting line answers with Cloudflare Workers AI (`@cf/meta/llama-3.3-70b-instruct-fp8-fast`, already bound as `AI`, covered by Cloudflare's free daily allowance). If an xAI key is set but the call fails (for example, out of credit), it falls back to the free model for that reply instead of going silent. Replies are capped at 200 tokens to suit SMS.

## Addendum 2 (waitlist, coupons, marketing tabs, caps, product sheet)

82. **Waitlist is the default public mode.** `launch_mode` (`waitlist` | `open`) lives in `site_settings`, and anything other than a clear `open` (slow request, error, missing row) shows the waitlist, so a pay button can never appear early. The public site reads it from `GET /api/site/config`. Sign-ups go through the `waitlist_join()` RPC: it takes an advisory lock, dedupes by lower-cased email, rate-limits 8 per hour per hashed IP, and gives a founding spot while fewer than 100 exist. The honeypot field is named `website`.
83. **Test mode holds MailerLite.** With `DRY_RUN` on, sign-ups are saved and counted, but nothing is pushed to MailerLite and "Launch" only previews the campaign. Rows show "not in MailerLite yet" and "Sync to MailerLite" catches them up once test mode is off and `MAILERLITE_API_KEY` is set. Launch creates a campaign **draft** only; nothing is sent until Marq presses Send in MailerLite.
84. **Founding offer is $19.99/mo for life, first 100, first month free.** It replaces the old $29 default in `OFFER_DEFAULTS` and the idea bank. The counter on the site is live from the `waitlist` table.
85. **Stripe: the connector is live-only, so no Stripe objects were created from here.** The Stripe MCP can't reach test mode (it answers 422), and the rule is no live-mode changes during the build. The four starting codes (MARQ20, FOUNDING, FAMILY, COMEBACK) are saved as drafts in `coupons`. The Coupons screen pushes them to Stripe with `STRIPE_TEST_SECRET_KEY` while `DRY_RUN` is on and `STRIPE_SECRET_KEY` once it's off. Test and live Stripe ids are kept in separate columns, so switching modes never overwrites either. Codes are paused rather than deleted.
86. **Checkout applies codes automatically.** A typed code, the code saved on the waitlist row, or FOUNDING for a founding spot (matched by email) is attached as a promotion code when checkout starts. A visitor's `?code=` is kept in localStorage (`mm_code`) so it survives navigation. Revenue per code is recorded on `invoice.paid` into `coupon_revenue`.
87. **One marketing engine, two tabs.** `mkt_brands` carries a `brand_type` (product / app / business / client). E-commerce → Marketing shows `product` brands and Made by Marq → Marketing shows `app`, `business` and `client`; both render the same `BrandMarketing` view over new per-brand ideas and plans tables. Product and client brands are derived from existing brands rather than copied. Masterminds is seeded as an `app` brand with the goal "grow the waitlist" and starter ideas; Made by Marq is seeded as a `business` brand. The old idea and plan tables are untouched (they held 0 rows to copy).
88. **Spending caps.** Defaults: e-commerce $50, Masterminds marketing $50, Higgsfield $15 **inside** e-commerce (a Higgsfield spend must fit both caps), Parallel $15, xAI $5, Twilio $10. Anthropic keeps its daily per-domain caps and raises an amber flag at $40 for the month. 80% of a cap is an amber flag, 100% blocks and is a red flag. The owner's stored caps are only replaced if they still equal the old defaults (schema_131 matched 0 rows, so nothing was overwritten).
89. **"Off until the first real sale"** applies to Higgsfield video, domains after the first site, and paid promotion for e-commerce products. A real sale means an `ecom_orders` row with a brand and a total above 0 (test orders excluded). The check runs only for actions that ask for it.
90. **Twilio and xAI are off by default.** Texting returns a clear "off until Twilio approves the number" unless `TWILIO_LIVE` is `1`. Grok only answers if an xAI key is set, the $5 cap allows it and `DRY_RUN` allows it; otherwise (or on any failure) the free Workers AI model answers.
91. **"Fits $50 budget" means a sample plus the site's domain.** Supplier cost + shipping + a $12 domain must be $50 or less. It is a hard rule for the nightly pitch (with the $10 profit and 35% margin floors) and an optional filter on the Product sheet next to a "$10 & 35% floor" filter. The thresholds live in `src/data/ecomProducts.ts` and are shared by the app and the Worker.
92. **"I want to test this one" bypasses the filters on purpose.** `POST /api/engine/test-product` makes a brand from any product's own numbers, links it, and queues the same Brand Lab and Supplier Finder runs an approved pitch does. It's safe to tap twice (it returns the existing brand). If the product is over budget it says so, and each later spend waits for approval.

## Addendum 4 (Contacts crash, error-screen game)

93. **Contacts crash: fixed at the shared helper and at the data edge.** The `e.split` error came from the `initials()` helpers (one in `screens/v2/util.ts`, copies in Shell, Home, Inbox and Classroom) being handed a contact whose name is `null`. All five now accept `null`/`undefined`. Contacts also pass through `normalizeContact` (`src/data/contactsPure.ts`) on load, so null name/tags/lists become `''`/`[]`. Contact search and the two other `.name.` callers were guarded too. I did not add a column default or change any data: the People-lists work lives in other tables and no migration was needed.
94. **Error-screen game is original and lazy.** The bot is an accent block with an "M"; obstacles are a bug, an error box, a spinner and a `null`. It's canvas + `requestAnimationFrame`, a separate lazy chunk (about 2.5 kB gzipped), themed from CSS tokens, pauses when the tab is hidden, waits for a tap under `prefers-reduced-motion`, and has its own error boundary so the plain error screen is the fallback. The high score is stored under `mm:runner-hi` inside try/catch. Reload stays above the game. The app has no offline screen today, so there was nothing to add there.

## Addendum 3 (Approvals tab, rich product cards)

95. **Approvals is its own E-commerce module** (`ecom-approvals`, right under Products) with a pending-count badge on its sidebar row (new `usePendingApprovals`, refreshed every minute and on focus). Inbox now holds customer email and order problems only. The approval notification links (pitch, brand directions, store preview), HQ's approval links, the overview's "Review all" and the Scout message on Products all open the new tab. I kept the Marketing tab where it was (after Orders), so the order is Products, Approvals, Sites, Orders, Marketing, Office, Inbox, Client Stores.
96. **One approval per Scout find** (`product_card`), replacing the one big `scout_products` batch. A find carries its row (with `detail.card`), a verdict and a summary. Old pending `scout_products` approvals still work. Approving a find saves it to the sheet and runs the same pipeline as "I want to test this one" (brand, then Brand Lab and Supplier Finder). Finds already on the sheet, or already waiting, are skipped.
97. **Supplier Finder + Analyst run before a find reaches Approvals** as one combined pass (`worker/lib/enrich.ts`): one Parallel search and one Claude call per product, under the normal daily caps. I folded the two workers into one call per product to keep cost near one call per find; they still show as the Analyst in the Office. If a cap or error stops it, the gaps become "Not found: reason" and the card offers **Find the missing numbers** (`POST /api/engine/enrich`, for a find or a sheet product). Hand-typed prices and costs are never overwritten.
98. **Why rows had 0/10 and no price:** the Scout prompt's example JSON used `"sell_price":0` and `"score":0`, and the model copied the zeros. The example now uses `null`, and the parser treats any 0 price, cost or score as unknown.
99. **Blocked finds stay visible.** Branded or knockoff names (including "X-style", where X isn't an ordinary look word like Retro or Vintage), supplements and ingestibles, cosmetics with health claims, medical devices and the earlier prohibited list now mark a find **Blocked** with the reason instead of dropping it. A blocked card can only be dismissed, and the approval applier refuses it too. The check runs on the sheet as well, so products already on it (tarte, Toplux Magnesium) show as Blocked. It is keyword-based, so a false alarm can be dismissed and re-added by hand.

101. **Verdict:** BLOCKED, else SKIP when under $10 profit or 35% margin, a red risk, fading, or a score under 5; GO when it fits the $50 budget, scores 7 or more, isn't flat and has no yellow warnings other than ship time; otherwise MAYBE.
